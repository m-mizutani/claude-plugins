# spec実装 + レビュー指摘対応 + PR作成

spec を実装し、実装が spec を満たしていることを照合し、コードレビューの指摘に対応し、PR を作成して CI を確認するまでを1つの作業とする。

このスキルで最も多い失敗は、spec に書かれた項目の実装漏れである。「一通り実装した」という感触は完了の根拠にならない。5. の照合で、spec の各項目に対応する実装の実体を示せることが完了の条件である。

実装に支障がある問題が起きない限り、最後まで作業を続ける。エラー、タイムアウト、失敗するテストは、原因を調べて解決する対象であり、停止する理由ではない。停止してユーザーの判断を求めるのは、このスキルが「判断を求める」と定めた場合と、取り消せない操作の前だけである。

# 1. specを特定する

spec は、これまでの会話で作成・合意したものを指す。通常は `Artifact` として公開済みで、実体は `.spec/{slug}/spec.html` にある。

- 引数でファイルパスや Artifact の URL が与えられた場合は、それを spec とする
- 会話中に spec がある場合はそれを使う。再公開に使うため、実体のローカルパスを確認しておく
- 会話に spec がない場合は、ブランチ名の `/` より後を slug として `.spec/{slug}/spec.html` を探す。なければ `.spec/{slug}/spec.md`、それもなければ `.cckiro/specs/{slug}/` 以下の Markdown を探す

spec を特定したら、1章から5章までを通読する。6章の実装計画は手順の見込みであり、満たすべき条件の一覧ではないため、6章だけを読んで着手しない。

## spec の章と、このスキルでの扱い

| 章 | 扱い |
|---|---|
| 1. 要求事項 | 要件を1件ずつ、実装の実体と対応づける |
| 2. 基本設計 | spec の小見出しごとに、実装の有無を外から判別できる項目を、実装の実体と対応づける |
| 3. 設計判断 | 採用案に従う。却下案を実装しない |
| 4. テスト計画 | 検証項目を1件ずつ、テスト名と対応づけ、成功を確認する |
| 5. インターフェースとスキーマの定義 | 記述どおりに実装する。変える必要が生じたら、その変更は実装せず、7. の「判断が必要」として扱う |
| 6. 実装計画 | 実装ステップで進捗を記録する。図のファイル構成は見込みであり、照合の対象にしない |

spec が定めていない内部構造（関数・型のシグネチャ、関数の呼び出し順、ファイルの分け方、補助的な型）は、既存コードの慣習に従って自分で決める。これについてユーザーに確認しない。

5章が「詳細設計」になっている旧構成の spec では、永続化スキーマと外的インターフェースの記述を上の5章と同じ扱いにし、内部のシグネチャと処理シーケンスは参考情報として扱う。

## デザインの所在を確認する

次のいずれかがあれば、デザインの提示があるものとして扱う。

- spec の2章に載っている変更後の画面（HTML と CSS で作られたもの、画像）
- ユーザーが会話中に貼った画面イメージ、モックの画像
- デザインファイルやモックの URL・パス
- 基準として示された既存画面のスクリーンショット

ユーザーが別途提示したデザインと spec の画面が食い違う場合は、ユーザーが提示したデザインを優先する。

## spec がない場合、または引数で実装内容を指示された場合

次のどちらかに当てはまる場合は、引数に書かれた指示を実装対象とする。spec の作成は求めない。

- spec が見つからず、引数に実装内容の指示がある
- spec の有無にかかわらず、ユーザーが引数の内容を実装するよう指示している

この場合、spec に関する手順（進捗の書き換え、再公開）は行わない。それ以外の手順（すべて実装する、照合を引数の指示に対して行う、検証を成功させる、レビューを実行して3区分で処理する、PR を作成する）は同じように行う。指示が複数の意味に読める場合は、実装の前にユーザーに確認する。指示の範囲を超える設計変更が必要になった場合は、実装せずユーザーに判断を求める。

spec も引数の指示もない場合は、実装に入らず `spec` スキルの Phase 1 に進む。

# 2. PRは原則1本にまとめる

PR は1本にまとめる。分割すると、各 PR の文脈・依存関係・マージ順の確認が必要になり、レビューの負荷が増えるためである。変更行数や変更ファイル数が多いこと、段階的に実装したいことは、分割の理由にならない。

1本では成立しない事情がある場合に限り、分割の前にユーザーの許可を求める。1本にできない具体的な理由、PR の本数、各 PR に含める変更、依存関係とマージ順を示し、明示的な許可を得るまで分割に着手しない。spec に分割が書かれているだけでは許可とみなさない。ユーザーがその分割を許可済みなら、同じ許可を再び求めない。

許可を得て分割する場合は、次のとおりにする。

- stacked PR にする。2本目以降は直前の PR のブランチを base にして作る（`gh pr create --base <先行PRのブランチ>`）。各 PR の本文に、スタック内での位置、base branch、全体のマージ順を書く
- 完了は、分割した全 PR が作成され、それぞれの CI が成功していることを指す。4.〜8. を PR ごとに行い、全 PR を終えてから 9. の報告をまとめて行う
- 途中の PR に「判断が必要」な指摘が残った場合は、その PR を draft のままにして次の PR に進む。先行 PR のマージも待たない
- どの要件をどの PR で満たすかを対応づけて書き出す。分割の境界で要件が抜けやすいためである

# 3. 完了条件を `.spec/goal.md` に書く

実装に着手する前に、完了条件を `.spec/goal.md` に書き、作業中のチェックリストとして使う。spec の特定と PR の本数の確認が済んでいるので、次の内容を展開した形で1回で書く。書いたら内容をユーザーに1〜2文で伝え、承認を待たずに 4. へ進む。

- spec の実体パスと、PR の本数
- **1章の要件を1件1行。** 機能要件と非機能要件を、1件ずつチェックボックスにする。「全項目」という総称にしない。まとめると実装漏れを検出できなくなる
- **2章の項目を1件1行。** spec の小見出しごとに、実装の有無を外から判別できる項目（データモデルの変更、状態の持ち方、主要な処理の流れ、画面ごとの状態）を書き出す
- **4章の検証項目を1件1行。**
- **5章の定義を1件1行。** 「該当なし」の節は書かなくてよい
- デザインの提示がある場合は、その所在と、再現する画面と状態を1件1行。ない場合は「デザインの提示なし」
- 次の共通の条件

```markdown
- [ ] spec の全タスクが done になっている
- [ ] 変更した利用者向けの文章を確認し、直すべき問題が残っていない（対象がなければ「該当なし」）
- [ ] プロジェクトで定められた検証（テスト、lint）がすべて成功している
- [ ] コードレビューを実行し、全指摘を3区分で処理した
- [ ] 変更が commit・push され、PR が作成されている（判断が必要な指摘が残っていれば draft）
- [ ] PR の CI が成功している
- [ ] 照合の結果、3区分の報告、PR の URL を報告した
```

引数の指示を実装対象とする場合は、spec に関する条件の代わりに、指示の内容を1件1行で書く。

`.spec/` 以下は作業用のファイルであり、commit しない。

# 4. specをすべて実装する

- spec に書かれた内容をすべて実装する。順序は6章の実装ステップを目安にする
- 作業が1つ終わるたびに、進捗を書き換える（HTML は `<li class="task todo">` → `<li class="task done">`、Markdown は `- [ ]` → `- [x]`）。最後にまとめて書き換えない
- spec を書き換えたら、同じ `file_path` で `Artifact` を呼び直して再公開する（URL は変えない）。実装中に追加の指示を受けた場合も spec を更新する。6章の図と実際のファイル構成に差が出た場合は、図を更新する
- `// TODO` / `// FIXME`、仮実装、スタブを残さない
- 5章の定義の変更、または spec にない設計変更（特に永続化スキーマの変更）が必要になった場合は、その変更を実装せず、7. の「判断が必要」として扱う。その判断に依存しない作業は続ける。判断がないと残りの実装を進められない場合だけ、停止してユーザーに判断を求める
- 4章の検証項目は、対応するテストを書いて成功を確認した時点で、1件ずつ `task done` にする
- 利用者が読む文章（画面の文言、エラーメッセージ、CLI のヘルプ、ドキュメント、翻訳）を変えた場合は、実装の動作と一致しているか、対象と結果が読み取れるか、用語が統一されているかを確認する
- 実装が終わったら、プロジェクトで定められた検証を実行し、すべて成功させる

実装ステップをすべて終えても、実装は完了していない。実装ステップは spec 作成時点の見込みであり、要件を網羅している保証がないためである。検証の成功を確認したら 5. へ進む。

# 5. specと実装を照合する

spec の1章、2章、4章、5章をもう一度開いて読み、項目ごとに実装の実体を確認する。記憶や実装中の印象で判断しない。

- 各項目について、それを満たす実装の実体を `file:line`、識別子、テスト名で示す。示せない項目は未実装である
- 該当するコードを実際に読んで確認する
- 検証がすべて成功していることは、要件を満たしている根拠にならない。テストのない要件は、検証が成功していても未実装でありうる

結果を次の表に書く。この表を 9. の報告に載せる。

| spec の項目 | 章 | 実装の実体 | 状態 |
|---|---|---|---|
| R1 [要件をそのまま引用] | 1. 要求事項 | `path/to/file.go:120` の `FuncName` / テスト `TestXxx` | 実装済み |
| T3 [検証項目] | 4. テスト計画 | テスト `TestYyy` | 実装済み |
| [定義] | 5. インターフェースとスキーマの定義 | `migrations/0007.sql:3` | 記述どおり |

「実装済み」「記述どおり」以外の状態が1件でも残っている場合は、次の表に従う。

| 差分の性質 | 対応 |
|---|---|
| 実装していない、または足りない | 4. に戻って実装する。報告して終わりにしない |
| spec の記述と実装が食い違い、どちらが正しいかが明らか（5章以外） | 正しい側に合わせ、spec を更新して再公開する |
| 5章の定義と実装が食い違う | 実装を5章に合わせる。5章を変える必要がある場合は「判断が必要」として扱う |
| spec のとおりに実装すると別の要件と矛盾する、または設計上の判断が必要 | 7. の「判断が必要」として扱い、選択肢をユーザーに示す |

要件を自分の判断で縮小して「満たした」ことにしない。実装できない要件がある場合は、それを明示してユーザーの判断を求める。

## デザインの再現を照合する

デザインの提示がある場合は、そのデザインの再現を完了条件とする。「概ね同じ」は未達として扱い、差分を1件ずつ挙げて実装を直す。次の点をデザインと実装で突き合わせる。

- **要素の構成と並び順**: デザインの要素がすべてあり、順序と階層が一致しているか。デザインにない要素を足していないか
- **レイアウト**: 配置、整列、幅と高さの関係、余白
- **文言**: ラベル、見出し、プレースホルダ、エラーメッセージ、空の状態の文言が、デザインのとおりか
- **視覚スタイル**: 色、文字のサイズ・太さ・行間、角丸、境界線、影
- **状態**: デザインに示された全状態を実装しているか
- **画面幅と操作**: 画面幅ごとの変化、遷移、アニメーションの有無

アプリを起動できる場合は、画面を表示して確認する（`run` スキルが使える）。起動できない場合は、デザインのソースと実装のマークアップ・スタイルを要素単位で読み比べ、その方法で確認したことを報告に書く。

再現できない差分（デザインシステムの制約、技術的に実現できない表現、デザインの指定が曖昧な箇所）は、近い表現に置き換えて済ませず、7. の「判断が必要」として扱う。

# 6. レビューを実行する

`codex-review` スキルを引数なしで起動し、この実装の差分をレビューさせる。`codex-review` の「修正計画を示してユーザーの承認を待つ」手順は、このスキルの中では行わず、7. の仕分けに従って自分で処理を進める。

次のいずれかの場合は、組み込みの `code-review` スキルを引数なしで起動する（`--fix` は付けない）。切り替えたことを報告に書く。

- スキルの一覧に `codex-review` がない
- `codex` コマンドが PATH にない、または未ログインである
- `codex-review` を起動したが、`codex exec` が非ゼロで終了した

両方とも使えない場合は、そのことを報告に書いたうえで、自分で差分と周辺のコードを読んでレビューし、同じ3区分で処理する。レビューを実行できないことを理由に 7. 以降を省略しない。

# 7. 指摘を3つに分類する

指摘された `file:line` と周辺（呼び出し元、呼び出し先、既存のテスト）を実際に読み、プロジェクトの規則と spec に照らして仕分ける。記憶や一般論で分類しない。全件をいずれかに分類し、説明なく省略しない。

| 区分 | 該当する条件 | 対応 |
|------|---------|------|
| 確信が強い | 読んで指摘が事実だと確認でき、修正内容も1つに決まる。または、誤った指摘か対処済みだと確認できた | 修正する（誤った指摘は却下する） |
| 確信が弱い | 指摘は妥当だと考えるが、事実関係、影響範囲、修正方法のいずれかに不確かな点が残る | 修正し、論点と判断の理由を記録する |
| 判断が必要 | 設計、優先度、トレードオフの選択であり、ユーザーが決めるべきである | 修正せず保留し、選択肢を整理する |

- 5. の照合で「判断が必要」とした差分も、この区分に合流させる
- 修正したら検証を再実行し、成功を確認する
- 修正で spec の内容が変わる場合は、spec を更新して再公開する。要件・基本設計・デザインへの適合が変わる修正をした場合は、5. の該当する項目だけ照合をやり直す

# 8. PRを作成する

7. の修正まで終えたら、ユーザーに確認を求めず、commit・push・PR 作成まで進める。「判断が必要」が残っていても進める（draft にする）。

## ブランチ

- 作業ブランチにいる場合は、そのまま使う
- default branch（main/master）にいる場合は、`git checkout -b {type}/{slug}` でブランチを作ってから commit する。`type` は `feat` / `fix` / `refactor` / `perf` / `style` / `docs` / `test` / `ci` / `build` / `chore` / `revert` から選ぶ
- 分割した場合の2本目以降は、先行 PR のブランチから作る

## commit

- `git status` で変更を確認し、`git add <ファイルパス>` でファイルを指定して追加する。`git add .` と `git add -A` は、意図しないファイルを含めるため使わない
- `.spec/` 以下は commit しない
- commit message は `<type>: <subject>` の形式で1行だけにする。本文と `Co-Authored-By` などの付帯情報は付けない
- push 済みの commit を `--amend` したり force push したりしない。追加の commit として積む

## PR

- `git push -u origin <branch>` で push する
- `gh pr view --json url,state,isDraft` で、現在のブランチに open の PR があるか確認する。ある場合は新しく作らず、本文が実装と食い違っていれば `gh pr edit` で更新する。ない場合は `gh pr create` で作る
- 「判断が必要」が1件でも残っている場合は `--draft` を付け、本文の末尾に「保留中の論点」として各件を選択肢付きで書く
- タイトルは英語、70文字以内、`<type>: <subject>` の形式にする。本文も英語で、変更の背景、変更内容の要約、検証方法（実行した検証と、5. の照合の方法）を書く。`🤖 Generated with ...` のようなフッタは付けない
- spec の URL は、リポジトリが private の場合だけ本文に載せる（`gh repo view --json isPrivate` で確認する）

## CI

- `gh pr checks --watch` で CI の結果を確認する
- 失敗があれば原因を調べて直し、追加の commit を push して再び確認する。CI が成功していない状態で完了を報告しない。調査と修正には `check-pr` スキルを使える

分割した残りの PR がある場合は、CI の成功を確認したら 4. に戻り、次の PR に着手する。

# 9. 報告する

経過を見ていない人が読んで意味が通るように書く。作業中に自分で作った用語や略称を使わず、対象を `file:line` か実在する識別子で示す。

- **spec との照合**: 5. の照合表を、全項目を省略せずに載せる。「すべて実装した」という総括だけにしない。デザインの提示があった場合は、確認方法（表示して確認したか、ソースを読み比べたか）と、残っている差分の有無を書く。なかった場合は「デザインの提示なし」と書く
- **レビュー指摘**: 3区分ごとに書く。該当が0件の区分も「なし」と書く
  - 確信が強いもの: 修正の要約を1件1行。却下したものは、却下したことと理由を1行
  - 確信が弱いもの: 論点、その判断をした理由、行った修正
  - 判断が必要なもの: 選択肢と、それぞれの利点と欠点。選択肢に整理できない場合は、何が不確かかを示す
- **PR**: URL、draft かどうか、CI の結果。分割した場合は、マージ順に全 PR の URL・base branch・draft かどうか・CI の結果を並べる

「判断が必要」が1件でもある場合は、全 PR を出し終えたこの時点でユーザーの判断を待つ。自分でどちらかを選んで実装しない。判断が出たら、それを実装して該当する PR のブランチに push し、CI の成功を確認してから `gh pr ready` で draft を解除する。

# 10. `.spec/goal.md` を削除する

9. の報告を出し終えた後に、`.spec/goal.md` を削除する。未達の条件を残したまま削除して、完了したことにしない。「判断が必要」が残って判断待ちに入る場合も、そこまでが完了条件なので削除する。
