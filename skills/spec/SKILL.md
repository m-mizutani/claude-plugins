# spec-driven development 計画ワークフロー

このスキルの範囲は、spec の作成・更新と、ユーザーの承認を得るところまでである。**このスキルの中では実装しない。** 実装・レビュー・commit・push・PR作成は `implement` スキルが担当する。

計画や承認待ちの後に、ユーザーが `/implement`、または対象と内容を明示した実装・続行・完了を指示した場合は、その指示を承認として扱い、`implement` スキルへ移る。同じ内容の承認を再び求めず、spec がないことだけを理由に spec の作成を要求しない。その指示は、破壊的な操作、マージ、デプロイ、依頼範囲外の変更までは許可していない。

# 状況判定

次を確認し、作業段階を判定してユーザーに伝えてから作業を始める。

1. `git branch --show-current` で現在のブランチ名を取得する
2. ブランチ名の `/` より後を slug とする（例: `feat/create-article-component` → `create-article-component`）
3. `.spec/{slug}/spec.html` があるか確認する
4. ある場合は進捗を確認する（`class="task done"` が完了、`class="task todo"` が未完了）。6章の実装ステップと4章の検証項目を分けて数える

`.spec/{slug}/spec.md` がある場合、それは Markdown 形式で作られた spec である。新たに `spec.html` を作らず、その `spec.md` を spec として読み、進捗も `- [ ]` / `- [x]` を書き換えて管理する。以降の「spec ファイル」はこの `spec.md` を指す。

| 条件 | 段階 |
|------|------|
| spec がない | Phase 1: spec作成（main/master にいる場合はブランチを作る） |
| 作業ブランチにいて spec がある | Phase 2: 既存specの点検 |

どちらを通っても、最後は Phase 3（実装への引き渡し）で終わる。

# Phase 1: spec作成

## ブランチの準備

- main/master にいる場合は、リモートと同期してから `git checkout -b {type}/{slug}` でブランチを作る。slug はタスクの内容から決める（例:「記事コンポーネントを作成する」→ `create-article-component`）。`type` は `feat`, `fix`, `refactor`, `perf`, `style`, `docs`, `test`, `ci`, `build`, `chore`, `revert` から選ぶ
- 既に作業ブランチにいる場合は、そのブランチを使う

## spec の形式

spec は HTML で `.spec/{slug}/spec.html` に書き、`Artifact` ツールで公開する。図を inline SVG で表示でき、ユーザーが URL で確認できるためである。

- 書く前に `artifact-design` スキルを読み込み、デザインにかける作業量はそのガイドに従う
- このスキルのディレクトリ（スキルの起動時に base directory として示される）にある `template.html` を読み、出発点にする。雛形の2章の小見出しと図は、設計に合わせて置き換える。`template.html` を読めない場合は、この節のクラス名と「章ごとの記述基準」の章構成を満たす HTML を自分で書く
- `spec.html` にはページの中身だけを書く。`<!doctype>` / `<html>` / `<head>` / `<body>` は書かない（公開時に自動で付く）
- 本文は日本語で書く
- 進捗は `<li class="task todo">` / `<li class="task done">` で表す。`implement` スキルがこのクラス名を書き換えて進捗を記録する
- ユーザーの判断が必要な箇所は `<div class="decide">` の callout で表す（後述）

`Artifact` ツールが使えない場合（ツールが一覧にない、公開が失敗する）は、ユーザーに判断を求めず、次の順で使える最初の形式にする。どの形式を使ったかと、`Artifact` を使えなかった理由を、報告に一文で書く。以降の「公開」「再公開」「URL」は、選んだ形式での書き込み・表示とファイルパスに読み替える。

1. **ローカルの HTML**: HTML を公開・表示できる別の手段があればそれを使う。なければ `.spec/{slug}/spec.html` を完全な HTML 文書（`<!doctype html>`、`<meta charset="utf-8">`、viewport の `<meta>` を含む）として書き、ブラウザで開くコマンドをユーザーに示す。雛形の中身を `<body>` に入れ、`<title>` と、背景色・文字色の指定を加える。`artifact-design` スキルが使えない場合も HTML で書く
2. **Markdown**: HTML ファイルを書けない、または表示する手段がまったくない場合に限り、`.spec/{slug}/spec.md` に書く。章構成は同じにし、進捗は `- [ ]` / `- [x]`、要判断は `> **要判断**` で始まる引用ブロックで書く。図は表と文章で表す

## spec に書く内容の区分

spec に書くのは、実装の前にユーザーが承認する必要がある情報と、コード変更の概略である。実際のコードを読めば決まる情報は書かず、実装時に実装者が決める。

| spec で確定する | 実装時に実装者が決める（spec に書かない） |
|---|---|
| 何を満たせば完成か。概念、データ構造、処理の関係と動作。選択肢のあった判断。外から観測できる振る舞いと検証方法。この変更の外から依存される定義。どのファイルをどう変えるかの概略 | 関数・型のシグネチャ（影響が明らかに大きいものを除く）、関数の呼び出し順、ファイルごとの編集内容、補助的な型、UI コンポーネントの分割 |

右の情報を書かない理由は、spec の作成時にはコンパイルもテストもされておらず、実装時に実際のコードを読んだ実装者のほうが正確に決められるためである。ユーザーが spec から得たいのは、設計の理解とコード変更の概略であり、編集の指示ではない。

spec の合格基準は2つある。spec だけを渡された別の実装者が、設計上の判断をやり直さずに設計の意図どおり実装できること。2章だけを読んだ人が、変更する対象の構造と動作を説明できること。

## 章ごとの記述基準

spec は次の6章で構成する。`implement` スキルが章番号と章名で参照するため、章名と順序は変えない。

| # | 章 | 書く内容 |
|---|---|---|
| 1 | 要求事項 | 何を満たせば完成か |
| 2 | 基本設計 | どの対象の構造と動作をどう変えるか |
| 3 | 設計判断 | 選択肢があった箇所で、何を採用し、何を却下し、なぜそうしたか |
| 4 | テスト計画 | 何を検証できれば、設計どおりに動いていると言えるか |
| 5 | インターフェースとスキーマの定義 | この変更の外から依存される定義 |
| 6 | 実装計画 | どのファイルをどう変えるかの概略と、実装の順序 |

### 1章 要求事項

機能要件、非機能要件、制約事項を書く。機能要件と非機能要件には `R1` のような通し番号を付ける。4章の図と `implement` の照合が、この番号で要件を参照する。

### 2章 基本設計

2章は、設計を理解するうえで最も重要な概念と、その関係・動作を、読者が説明できるようにする章である。構成要素、変更ファイル、型の一覧を埋める章ではない。書く前に関連するコードと要求を読み、次を検討する。

1. **理解の中心になる事項を選ぶ。** データ構造、アルゴリズム、処理プロセス、状態遷移、責務の分担のうち、何を理解しないとこの設計が要求を満たす理由が分からないかを特定する
2. **混同されやすい概念を区別する。** 各概念が何を表し、1件が何に対応し、他の概念とどう関係するかを説明する。保存するデータと処理対象、処理の定義と1回の実行のように異なるものを、同じ語や同じ箱で表さない
3. **説明の順序を選ぶ。** 読者が知っている前提から、重要な概念、その関係、動作、要求を満たす理由へ進む。冒頭に設計全体の考え方を短く書く
4. **具体例で動作を追う。** 具体的な入力や状態を1つ選び、選択・判定・更新・実行・終了を、処理前から処理後まで追えるようにする

小見出し、順序、節の数は、設計の理解に必要な内容から決める。次は検討するときの観点であり、同名の節を機械的に作るための一覧ではない。

| 観点 | 読者が理解できるようにする内容 |
| --- | --- |
| データ構造 | 何を1件として保存・処理するか、キーと値、順序と優先順位、関係と多重度、一意性、従属と寿命。保存する情報と保存しない情報の区別 |
| アルゴリズム | 入力、選択・判定の条件、処理順、更新、出力、終了条件。性能が要件なら、何の件数に応じて処理量が増えるか |
| 処理プロセスと状態 | 起点、実行する主体、順序、状態遷移、再試行と終了。同時実行時に誰が何を占有し、いつ解放するか。制限や予算を適用する単位 |
| 構成と責務 | 上のデータと処理をどの構成要素が担当し、どの境界で情報や制御を渡すか。一覧表は関係を説明した後の補足にする |
| 変更前後と要求 | 既存のどの構造・動作をどう変え、何を維持するか。その変更で要求を満たせる理由 |

エージェントや LLM を使う設計では、実行の単位、履歴の継承、固定の手順と可変の手順、終了条件、プロンプトの分担、ツールの範囲と上限、モデルの割り当ても説明する。

**データモデルは DB スキーマに限らない。** 型、JSON、メッセージ、処理中の状態、保存形式、キーの意味、データどうしの関係や多重度が変わる場合は、DB のテーブルが変わらなくても、2章にデータモデルを説明する項目と図を設ける。関係するデータ全体を示し、変更前後の単位、キー、参照関係、多重度、保存先の違いを説明する。保存しないデータも、誰が生成し、誰が読み、いつ失われるかを説明する。

**図。** 2章は各項目に図を入れる。章全体に全体図を1枚置くことは、各項目の図を省く理由にならない。図を省略できるのは、概念の説明を要さず、かつ文字だけで説明する必要がある項目に限り、その場合は理由を一文で示す。

- 図ごとに答える問いを決める。データの形、分岐、処理順序、状態遷移、同時実行の範囲は、別の図が必要になることがある
- 図の前に、その図で理解する関係や動作を説明する。図の後に、読み取るべき条件を書く
- 箱が概念、データ1件、プロセス、実行1回のどれを表すか、矢印が参照、データの移動、呼び出し、状態遷移のどれを表すかを、ラベルか凡例で示す
- 複数の図で同じ概念の名称を揃える。具体例の入力・時刻・件数・状態を、本文と図で一致させる
- 図は inline SVG または HTML+CSS で作る。mermaid と ASCII Art は使わない。箱と矢印で表せる関係は図にする。項目どうしの対応や、変更前後の値の対比は、表を `<figure>` に入れて図として扱ってよい

**UI を変える場合は、spec の作成者がデザイナの役割を担い、変更後のデザインを自分で作って spec に載せる。** デザインの確定を spec の承認に含めるためである。ここでの UI は、Web・モバイル・デスクトップの画面を指す。CLI の出力とヘルプの文言は、5章の外的インターフェースに書く。

- 変更対象の画面のマークアップ、スタイル、デザイントークン、共通コンポーネントを読み、変更後のデザインはそのプロジェクトの既存の色・余白・タイポグラフィ・コンポーネントで作る
- 変更前の画面を示す。アプリを起動できる場合は、画面と状態ごとにスクリーンショットを撮り（`run` スキルが使える）、`.spec/{slug}/screenshots/` に保存して `spec.html` から相対パス（例: `screenshots/list-empty.png`）で参照する。公開時は `Artifact` の `files` に、公開するパス `screenshots/list-empty.png` と元のファイル `.spec/{slug}/screenshots/list-empty.png` の対応を渡す。撮影できない場合は、コードから読み取った現在の構成を説明し、撮影していないことを明記して進める
- 変更後の画面を、画面ごと・状態ごと（初期表示、読み込み中、空、エラー、選択中、無効など、その画面が取りうる状態すべて）に HTML と CSS で作り、2章に載せる。文言は実際に表示する文言を書く。文章による説明だけで済ませない
- 変更前と変更後を並べ、要素ごとに、何をどう変えたかと、対応する要件の番号を書く
- 複数の案があり、ユーザーの意図で結果が変わる箇所は、案を画面として並べて `decide` の callout で示す
- ユーザーが別途デザイン（モック、デザインファイル）を提示した場合は、そのデザインを優先し、提示されていない画面と状態だけを作る

### 3章 設計判断

選択肢が複数あった箇所（状態の保存先、同期か非同期か、型の受け渡し方、認証の流れ、新しい名前）について、採用案、却下案、理由を書く。実装者が同じ検討を繰り返さないためである。

### 4章 テスト計画

外から観測できる振る舞いを書く。境界条件とエラーケースは、この章だけに書く。

- **図1枚で全体を示す。** 行に要件または振る舞い、列にテストの置き場所（テストファイルまたはテストの水準）を並べ、交差するセルに検証項目を短いラベルで書く。ラベルは正常系・境界値・異常系を色で区別する。検証しないセルは「―」にし、検証されない要件が見えるようにする
- 図の下の折りたたみ（`<details>`）に、各検証項目を1行ずつ `task todo` で書く。1行は「入力・状態 → 期待する結果」の形にする
- 正常系だけの計画にしない

### 5章 インターフェースとスキーマの定義

この変更の外にあるもの（保存済みのデータ、変更しないコード、利用者、運用者、外部サービス）が依存する定義だけを書く。誤ると実装後の修正では済まないため、名前・型・値・既定値まで確定する。節は次の3つで、書く定義がない節には「該当なし」と書く。

- **永続化スキーマとマイグレーション**: DB のテーブルと列、ファイルやオブジェクトストレージの保存形式、メッセージの形式、キャッシュのキー。変更がある場合は、既存データの扱い、後方互換性、ロールバックの可否も書く
- **外的インターフェース**: プログラムを外から使う人やシステムが触れる境界。API・エンドポイント、設定項目、環境変数、CLI のフラグと引数、外部サービスとの連携と必要な権限
- **重要な公開シグネチャ**: コードどうしの境界のうち、影響が明らかに大きいものだけを書く。他のリポジトリから使われるライブラリの公開 API、複数の型が実装するインターフェース、変更すると今回触れない多数の呼び出し元の修正が必要になる関数が当たる。網羅はしない

### 6章 実装計画

- **図1枚で全体を示す。** 変更するファイルまたはディレクトリを箱で表し、新規・変更・削除の区別、箱ごとの変更の要点（1〜3行）、箱どうしの依存関係を示す
- 図の下に、進捗を記録するための実装ステップを数件、`task todo` で並べる。ファイルごとの編集指示とファイルごとのチェックリストは書かない
- 図のファイル構成は spec 作成時点の見込みである。実装者は、図にないファイルの追加や分割をユーザーに確認せずに行える

## 既存コードと未決の事項

- **既存コードに触れる設計は、実際のコードとスキーマを読んでから書く。** 既存の型・関数・パスは実在する名前で参照する。読んでいない箇所を推測で書かない
- **設計上の判断を先送りしない。** 「実装時に確定する」「あとで決める」「必要に応じて」と書かず、名前を「等」「など」で曖昧にしない。この規則は、「spec に書く内容の区分」の表で「spec で確定する」とした情報に適用する。「実装時に実装者が決める」とした情報は、先送りではなく spec の対象外である
- 既存の構造や動作を変える箇所は、変更前の現状と変更後を対比して書く
- 情報が足りず決められない項目は、ユーザーの判断を求める。`decision-brief` スキルが使える場合は、それで選択肢と根拠を示す。spec には該当する位置（章末や文書末ではなく、その判断が関わる箇所）に `<div class="decide">` の callout を置き、決める事項、名前を付けた選択肢、各案を採用した場合に起きること、推奨案と理由を書く。判断が出るまでの本文は推奨案を前提に書き、どの記述が推奨案を前提にしているかを callout に書く。判断が出たら callout を削除し、本文と3章に反映する。callout が残っている spec は下書きであり、確定済みとして実装へ進めない

## 記述の詳しさの例

次は詳しさの水準を示す例であり、小見出しや順序の雛形ではない。識別子は見本なので、実際に読んだコードの名前で書く。

- **2章 / 説明の構成**: ❌「構成要素と責務の表 → 全体の接続図 → テーブルの一覧」。✅ 定期処理の設計なら、まず「次に処理する対象を選ぶデータ」と「実際に実行する仕事」が同じか異なるかを説明し、次にキーと時刻の具体例で対象の選択と更新を追う。構成と責務の表は補足にする
- **2章 / データモデル**: ❌「計画テーブルと変更項目テーブルを追加する」。✅「エンティティが2つ増える。計画は1回の相談のまとまりで、テナントに従属し、対象の絞り込み条件と状態を持つ。変更項目は計画に従属する1件の変更案で、既存のルールを0〜1件参照する。計画1件に変更項目は0〜N件あり、計画が破棄されると変更項目も消える。既存のルールのモデルは変更しない」
- **2章 / 状態**: ❌「計画の状態をDBに保持する」。✅「計画は `open` → `applied` / `discarded` の3状態を取る。状態を書き換えるのは適用処理と破棄処理の2経路だけで、エージェントは変更項目の追加しか行わない」
- **2章 / エージェント**: ❌「エージェントが指示を受けて変更案を出す」。✅「1つの指示が1回の実行に対応し、次の指示では前回の会話を引き継いで新たに実行する。手順は『現状把握 → 意図の分解 → 対象の確定 → 根拠の収集 → 提案 → 返答』の6つに固定し、3〜5番目は意図の数だけ繰り返す。待機状態は設けず、質問が必要な場合は返答に書いて実行を終える」

## 提示前の確認

公開の前に、追加のモデルやサブエージェントを呼ばず、自分で本文と図を読み直して次を確認する。満たさない項目は直してから公開する。

- 2章だけを読んで、主要な概念の関係と、具体例の動作を説明できるか。説明の中心が、構成要素やファイルの一覧になっていないか
- 型、JSON、状態、キー、保存形式、参照関係、多重度を変える場合に、そのデータモデルを2章の項目と図で説明したか
- 2章の各項目に図があるか。箱・矢印・凡例の意味と、本文と図の用語・例の値が一致しているか
- UI を変える場合に、変更後の画面を、取りうる状態すべてについて作ったか
- 4章と6章に図が1枚ずつあり、4章の図から、検証されない要件が読み取れるか
- 4章の図にある検証項目の番号と、図の下の折りたたみに書いた検証項目の番号が、1件ずつ対応しているか
- 5章の各節が、定義を確定しているか、「該当なし」と書いているか。5章の変更に対応する説明が2章にあるか
- 内部のシグネチャ、関数の呼び出し順、ファイルごとの編集指示を書いていないか
- 先送りの表現、曖昧な名前、変更前後の対比の不足、推測で書いた既存コードの名前が残っていないか
- `decide` の callout が、判断が必要な箇所にだけ残っているか

## 公開とレビュー依頼

1. `Artifact` ツールに `file_path` として `.spec/{slug}/spec.html` を渡して公開する。初回は `title` にタスク名の spec であることが分かる名前、`icon` に `document` を指定する。返された URL をユーザーに示す。修正したら同じ `file_path` で再公開し、URL を変えない
2. 表示を確認する手段がある場合は、図と本文の対応、文字の重なりや切れ、狭い幅での読みやすさを確認し、問題を直して再公開する。確認できない場合は、その範囲を未確認として報告する
3. **レビューを依頼し、ユーザーの明示的な承認を得るまで停止する。** `decide` の callout が残っている場合は、依頼の文でも、どの章のどの点に判断が必要かを一覧で示す

承認を得たら Phase 3 へ進む。

# Phase 2: 既存specの点検

- spec ファイルを読み、進捗をユーザーに伝える
- 章構成が現在の6章になっているか確認する。旧構成（5章が「詳細設計」）の spec は、実装が始まっているかどうかで扱いを分ける
  - `task done` が1件でもある場合は、章構成を組み替えない。実装者が参照している記述と記録済みの進捗を失わないためである。`implement` スキルは旧構成の spec をそのまま扱える
  - `task done` が1件もない場合は、現在の6章に組み替える。永続化スキーマと外的インターフェースは5章に残し、境界条件とエラーケースは4章へ移す。内部のシグネチャと処理シーケンスは、2章の説明に必要なものを2章へ移し、残りを削除する。削除した内容があることをユーザーに伝える
- 「提示前の確認」に沿って確認し、不足を直す
- 直した場合は同じ `file_path` で再公開し、差分をユーザーに伝えて承認を得る。直す必要がなかった場合はそう伝える

確認が済んだら Phase 3 へ進む。

# Phase 3: 実装への引き渡し

spec が承認された（または Phase 2 で妥当性を確認した）ら、次の2つを行って停止する。

1. spec の URL と実体パス（`.spec/{slug}/spec.html`）を示す
2. 「実装は `/implement` を実行してください」と案内する

ユーザーが「そのまま実装して」と指示した場合も、このスキルの中では実装せず、`implement` スキルを起動する。実装の見通しや懸念を伝える必要がある場合は、1〜2文にまとめる。

`/compact` は、コンテキストが実際に逼迫している場合に限って提案する。Phase 1 の議論には、spec に書き切れなかった文脈（却下案の評価、ユーザーの意図）が残っており、実装中の判断に役立つ。
